## Description

`tests/vectors` is a copy of `mica:docs/design/release-lock/vectors`, and until
now the only record of where it came from was a comment. The comment named mica
`19fbdce`, at which `expected.tsv` had 69 rows; the files beside it were the
84-row set of mica HEAD and had been for days. Nothing was wrong with the
vectors and nothing could have told a reader that.

The mechanism is the coordinator's ruling of 2026-09-20 for all four package
repositories: a consumer reads the vectors out of mica at a pinned commit and
refuses a difference, with the pin in a file named `vectors.pin` (uniform
basename, directory each repository's own, so a workspace-wide check is one
command rather than a maintained list of paths).

Direction is the part worth naming, because this repository already had the
other one: `mica-core`'s component contracts are bytes it produces and another
repository verifies. The vectors are bytes another repository produces and this
one must verify. Same mechanism, opposite direction, and the second direction is
the one that was missing everywhere.

## Shape

- `tests/vectors.pin` is `mica-vectors-pin v1` (spec 5, mica `c7fb6f17`): the
  header, then `REPOSITORY=` and `COMMIT=` in that order and nothing else, then
  a final newline. The commit is the full 40 hex; a short commit is refused,
  because a prefix is not a name a tree can be compared against. Its six
  canonical vectors (`vectors-pin/`) run beside the lock vectors, so the reader
  of the pin is held to the same standard as the reader of the lock.
- `src/vectors.ts`: the pin reader, the local tree as git blob names, mica's
  tree at the pinned commit from the GitHub tree API (mica is public; a token
  only raises the rate limit), and the comparison.
- The comparison is set equality **both directions** plus content. The extra
  file is the half that hides: a fixture the canonical no longer has stays green
  forever, because the reader and the fixture agree with each other and neither
  has been told the format moved (`mica-boards` is carrying exactly that today,
  a `mica-boards.x64.lock` naming a board that no longer exists).
- The gate is `bun src/container.ts vectors`, a step of the `check` job beside
  the build-env pin check. It is not part of `bun run test`: the tests run in a
  container with no network.

## Result

Landed 2026-09-20; the pin and the copy move together, most recently to mica
`5ce4656f` (143 files). It was first `735ebaa`, then `ddf4edc8`, which is the commit
that repairs the `bun-linux-uefi-x64.zip` rename artefact; the first pin was
`735ebaa`, cut two minutes before the repair landed and moved as soon as it
did. Four days of drift went unnoticed because nothing named a commit; two
minutes of it was visible immediately because something did. The provenance comment
in `tests/release-lock.test.ts` is gone; it points at the pin, which is checked.

And the aperture, learned the same day from a defect six fixtures wide that
every copy shared: **agreement between copies is not correctness of the
original**. This gate answers "did it travel intact" and cannot answer "was it
right when it left". Correctly sized rather than weakened.

Recorded with it, because this repository is the evidence for it: **a current
fixture set does not imply a current reader**. The reader here was four days
stale on the scope separator while these same 133 blobs were byte-identical to
canonical. The vector count answers a different question than the reader does.

The required subset is derivable — what this repository pins, plus what it
produces, plus the vectors that say what its own forms may not be — and it is a
floor, not a ceiling. This repository pins one unscoped producer and runs the
scoped, index, product, bundle and asset vectors anyway, because it emits the
lock that `mica-build`, `mica-podman` and `mica-core` read: a producer that
conforms only to what it consumes can emit a row nobody downstream accepts.

## Open: the copy, once this repository has an offline chain

The gate reads mica's tree over the network; what the copy buys is that the
*tests* run offline, not that the *check* does. `mica-podman`'s design keeps no
copy at all: it fetches mica at the pinned commit into the git-ignored source
cache and verifies HEAD is that commit, which git cannot fake, so a warm cache
needs no network and the checkout is the pin. Both designs therefore run
offline; the trade is drift against maintenance and not offline against online.

This repository has no `tools/repos.sh` yet -- it is why the four `repos/`
vectors are the only rows skipped. When the offline chain lands here, reading
mica out of that cache is the natural form, and whether to keep the copy at all
becomes a real question rather than an assumed one. Not decided now.
