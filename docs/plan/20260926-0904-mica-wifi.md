## Context

- Today a Wi-Fi root installs Debian's `wpasupplicant` 2:2.10-24 (3321 KiB, loads
  libnl-3, libnl-genl-3, libnl-route-3, libpcsclite, libdbus) and `hostapd` (1993 KiB),
  pinned for later stages in `upstream.pkgs`.
- `mica-build/producers/radio-wifi` already builds packages named `mica-wifi` and
  `mica-wifi-ap`: architecture `all`, no binaries, `Depends: wpasupplicant` and
  `hostapd`. They mask `wpa_supplicant.service`, its D-Bus alias and
  `hostapd.service`, ship `etc-wpa_supplicant.mount` and `etc-hostapd.mount` (the
  STATE binds), and `mica-regdb-reload.service`. `radio-wifi.pkgs` and
  `consumers.json` name both packages.
- micad drives `wpa_supplicant@<iface>.service` with
  `/etc/wpa_supplicant/wpa_supplicant-<iface>.conf`, and the AP reconciler drives
  `hostapd@<iface>.service`; scanning goes through the control socket (`SCAN`,
  `SCAN_RESULTS`, `SIGNAL_POLL`, `STATUS`).
- Debian's source is `wpa_2.10.orig.tar.xz` with 20 patches in
  `wpa_2.10-24.debian.tar.xz`, three of them CVE fixes (CVE-2023-52160,
  CVE-2022-37660, CVE-2024-5290). `hostapd@.service` is Debian's own file;
  `wpa_supplicant@.service` is upstream's, patched by Debian.
- Packages here follow mica-busybox and mica-systemd-boot: a Dockerfile whose
  `# mica-deb:` header declares `build=` and `sources=`, `source.<name>` rows
  committed in `locks/upstream.lock`, `build.<package>.*` rows from `pin-inputs`,
  and a version-locked `control`.

## Proposal

1. `debs/mica-wifi`: compiles `wpa_supplicant` and `wpa_cli` from `source.wpa` (the
   orig tarball) with the patches of `source.wpa-debian` applied in series order,
   over a committed `config`: `DRIVER_NL80211`, `LIBNL32` linked statically,
   `CTRL_IFACE`, `BACKEND=file`, `AP`, `BGSCAN_SIMPLE`, `IEEE80211W`, `SAE`,
   `TLS=openssl`, `GETRANDOM`, and nothing else. Payload: the two binaries,
   `wpa_supplicant@.service` rendered for `-Dnl80211`, and what the mica-build
   producer ships today (the masks, `etc-wpa_supplicant.mount` with its wants link,
   `mica-regdb-reload.service` with its wants link), copied byte-identical.
   `Depends` only on packages the base root already has (libc6, libssl3t64,
   rfkill and iw stay as they are today).
2. `debs/mica-wifi-ap`: the same source and patches, `hostapd` and `hostapd_cli`
   over its own `config` (nl80211, static libnl, `CTRL_IFACE`, OpenSSL, `SAE`,
   `IEEE80211W`, no RADIUS, accounting or VLAN), Debian's `hostapd@.service`, and
   the producer's hostapd mask and `etc-hostapd.mount`.
3. Build gates in each Dockerfile: the ELF machine of the target architecture, no
   `libnl`, `libdbus`, `libpcsclite` or `libreadline` in `NEEDED`, and the
   binary's `-v` naming 2.10.
4. `locks/upstream.lock`: `source.wpa` and `source.wpa-debian` from
   snapshot.debian.org, and the `build.mica-wifi.*` and `build.mica-wifi-ap.*`
   closure (pkg-config, libnl-3-dev, libnl-genl-3-dev, libssl-dev) from `pin-inputs`.
   `debs/consumers.pkgs` gains both names; tests pin their versions.
5. Verified by building both packages for amd64 and arm64 and reading the debs.

Phase 2, in mica-build and not in this task: retire `producers/radio-wifi`, point
`consumers.json` at the new paths, and pin the Base release that carries these
packages in the same change; then drop wpasupplicant, hostapd and their closure
from `upstream.pkgs` here.

## Risks

- **The names collide with mica-build's producer.** Until phase 2 lands, a
  mica-build that imports this Base release sees two `mica-wifi` packages. The
  Base release that carries them must be pinned by mica-build in the same change
  that retires the producer.
- arm64 compiles under emulation, several minutes per package.
- micad parity rests on the unit names and paths above; the unit files are taken
  from the patched source, not rewritten.
- A Debian security update to `wpa` is a bump of `source.wpa-debian` and of both
  package versions here.

## Scope

mica-system-base: two package directories (control, Dockerfile, config, units),
`locks/upstream.lock`, `debs/consumers.pkgs`, `tests/debs.test.ts`, docs.

## Alternatives

- Upstream hostap 2.11 (w1.fi) as the only source row: it carries the CVE fixes
  and is simpler, but leaves the version trixie's security team follows.
- One `mica-wifi` holding both daemons: a station-only board would then install
  hostapd, which mica-build split the packages to avoid.
- Include enterprise EAP (PEAP, TTLS, TLS, MSCHAPv2): +190 KiB; micad writes no
  EAP configuration today.

## Progress

2026-09-26: done as annotated, with one change from the proposal: libnl-3 and libnl-genl-3
are linked dynamically, since the base root already carries both (mica-system's closure) and
`iw` loads them; each build allows exactly libc, libcrypto, libnl-3 and libnl-genl-3.
Built for amd64 and arm64 (arm64 emulated), installed on the Base root of release
20260920-0832 with every symbol bound at start. The masks of `wpa_supplicant.service`, its
D-Bus alias and `hostapd.service` are not carried: no package ships those units any more.

## Annotations

2026-09-26, the user's decisions:

1. **Base owns Wi-Fi.** mica-wifi and mica-wifi-ap here take over what the mica-build producer
   ships; mica-build keeps no Wi-Fi packaging of its own. The transition (both repositories
   producing the names at once) is not a concern.
2. **mica-wifi-ap is built in the same change.**
3. **Upstream hostap, tracked like podman**: the latest release archive from w1.fi is the only
   source row; Debian's patch series is not applied.
4. **No enterprise EAP.**
